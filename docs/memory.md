### Process Lessons
- **LESSON (2026-08-26): Phases 0-2 were marked "✅ Done" but had NEVER actually been run.** First live boot of the backend required 5 root-cause fixes (reserved `metadata` attr, wrong registry import path, enum name/value mismatch, duplicate CREATE TYPE from ignored `create_type` kwarg, passlib/bcrypt breakage). Rule going forward: **mark an item verified only when it has actually been executed** — code existing on disk is not verification. Distinguish "code complete" from "runtime verified" in every checklist.
- **LESSON (2026-08-27): PowerShell 5.1 `Invoke-WebRequest` silently swallows exception response bodies.** When a non-2xx HTTP response is thrown as an exception, `$_.Exception.Response.GetResponseStream()` fails with "NonInteractive mode" error in PS 5.1 — the status code and body are lost. Fix: use `curl.exe` with `--data-binary @tempfile` for API testing scripts. The tempfile avoids PowerShell mangling double-quotes in JSON when passed via `-d`.
- **LESSON (2026-08-27): Backend Docker image is built, not volume-mounted.** Code changes to `backend/` are NOT reflected in the running container until `docker compose up -d --build backend worker` is run. Always rebuild after backend code changes before testing.
- **LESSON (2026-08-27): The frontend `npm run dev` "Win32 spawn error" was TRANSIENT, not structural.** When launched directly (`npm run dev` from `frontend/`, `package.json` script is plain `next dev`), Next.js 14.2.35 starts cleanly every time (Ready in ~2–16s). The `.bin/next{,cmd,ps1}` shims are intact; no orphaned `next` process held port 3000 (the 4 stray node processes were `chrome-devtools-mcp`, the browser MCP tool, unrelated to dev). Conclusion: do NOT modify package.json or add workarounds for this — it was an artifact of how the prior session invoked the process, not a real defect.
- **LESSON (2026-08-27): Puppeteer module resolution is file-relative to where the script lives.** `import "puppeteer"` only resolves when the script is under `frontend/` (puppeteer is installed only in `frontend/node_modules`). `scripts/verify-correlation-colors.mjs` actually throws `ERR_MODULE_NOT_FOUND: Cannot find package 'puppeteer'` when run — the recorded session-6 pass must have used a special invocation (NODE_PATH or a copy inside frontend). For repeatable browser verification, keep the script inside `frontend/` and run `node <script>.mjs` from there. RBAC browser script: `frontend/verify-rbac-viewer.mjs`.
- **LESSON (2026-08-28/session 12): pytest-asyncio 0.23.6 (pinned) does NOT support loop-scope config or loop-scope mark/fixture kwargs** (those arrived in 0.24). Worse, in strict mode it fails to unroll async **generator** fixtures — an `async def ... yield` fixture is passed to the test as the raw `async_generator`, raising `AttributeError: 'async_generator' object has no attribute ...`. Consequence: `test_health.py` and `test_auth_and_cases.py` (pre-existing, unmodified) FAIL because their `client` fixture is `@pytest.fixture async def client(): ... yield ac`. Workaround for new DB tests: **avoid async-generator fixtures** — seed + assert + dispose the engine inside each async test body (with try/finally cleanup), and dispose the global loop-bound engine at the end of each test so no stale asyncpg pool crosses event-loop boundaries. Also: running `asyncio.run()` from inside a pytest-asyncio test (already in a loop) raises — run the prepackaged `run_async`/`asyncio.run` code via `asyncio.to_thread`.
- **LESSON (2026-08-28/session 12): "Pipeline works" must be proven through the REAL async path, not just imports.** Scenario 1 E2E surfaced 5 bugs invisible to unit tests: (1) celery worker registered ZERO tasks (empty `__init__.py`), (2) `RuntimeError: Future attached to a different loop` — global loop-bound asyncpg pool reused across celery prefork loops, (3) normalized `LogEvent`s were ES-indexed but NEVER persisted to Postgres, so the AI engine (which reads Postgres `LogEvent`) saw 0 events, (4) concurrent AI runs (one per upload) duplicated Entity/Edge/Anomaly rows, (5) the timeline page requested `size=500` but the backend search endpoint capped `size` at `le=200` → HTTP 422 → **every case's timeline rendered "0 of 0 events / No events to display"**. Lesson: an "empty" UI page is often a 422 from a param mismatch — check the browser devtools/network for non-2xx before blaming the renderer.

### Session 12 — Pipeline bugs found & fixed during Scenario 1 E2E (each committed separately)
- **Bug #1 — Celery worker registered ZERO tasks.** `celery_app.autodiscover_tasks(["app.tasks"])` finds no `tasks.py`, and `app/tasks/__init__.py` was empty (0 bytes) → the worker showed `- empty -`, so no parse/AI task could ever run. **Fix:** `app/tasks/__init__.py` now `from app.tasks import ingestion_tasks, ai_tasks` (commit `2941ff1`). Worker now registers `tasks.parse_log_file` + `tasks.run_ai_correlation`, all 6 parsers.
- **Bug #2 — `RuntimeError: got Future attached to a different loop` in `run_ai_correlation`.** Celery prefork tasks each run in a fresh event loop, but the global SQLAlchemy async engine builds a loop-bound asyncpg pool reused across `asyncio.run()` loops. **Fix:** new `backend/app/tasks/runner.py` with `run_async(coro_factory)` → `asyncio.run`, disposing the engine in `finally`; both tasks now route through it (commit `0b6ed83`; task wiring also in `10b4f93`/`be4415f`).
- **Bug #3 — `LogEvent` rows were NEVER persisted to Postgres** (only ES-indexed). The AI engine reads Postgres `LogEvent`, so it saw 0 events (`log_events count = 0`) → no correlation/anomalies. **Fix:** `ingestion_tasks.parse_log_file` now persists every normalized event via extracted `persist_log_events(db, normalized)` (commit `10b4f93`).
- **Bug #4 — Duplicate Entity/Edge/Anomaly rows on concurrent AI runs.** Every upload enqueues its own `run_ai_correlation`; without guarding, racing runs accumulated duplicates. **Fix:** `ai_tasks.run_ai_pipeline` now takes `pg_advisory_xact_lock(hashtext('ai:{case_id}'))` then deletes existing Entity/CorrelationEdge/Anomaly for the case before rebuilding (idempotent). Extracted into `run_ai_pipeline(case_id)` for a direct regression test (commit `be4415f`).
- **Bug #5 — Timeline was EMPTY for every case.** The timeline page (React Query) requests `size=500`, but backend `routes/search.py` capped `size` at `le=200` → HTTP 422 → `0 of 0 events`. **Fix:** raised cap to `le=1000` (commit `2c95e61`). This is why the timeline appeared broken from the start.
- **Regression tests** for all 5: `backend/tests/test_pipeline_regressions.py` (5 tests, all pass) — commit `a94212f`. **Verify scripts:** `frontend/verify-zod-populated.mjs` (Zod on populated data) + `frontend/verify-scenario-e2e.mjs` (browser timeline + correlation) — commit `d9c96d2`.
